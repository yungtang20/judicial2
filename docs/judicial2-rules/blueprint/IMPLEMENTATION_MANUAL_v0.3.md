## 0. 執行規則（必讀）

1. **起點**：從目前 `main` 建立分支 `feature/flow-v0.3`。不得使用任何外部或非 repo 內的程式碼作為起點。
2. **唯讀**：不得修改 `rules/handbook/` 內任何檔案，包括 v19 正文。
3. **不得改寫法律內容**：不得新增、刪除、改寫手冊條文；不得自行判定罪名、告訴乃論、追訴期間。
4. **法律判斷由 LLM 執行**：程式只做機械檢查（見第 4 節）。程式不得以關鍵字或條件式推定罪章、路由、問句內容。
5. **既有 Gate 規則引擎不刪除**：`pipeline/gate1.py`、`gate2.py`、`gate3.py`、`run.py`、`web.py`、`evaluate.py` 維持原狀，不得修改其行為。新流程另建於 `pipeline/flow/`。
6. **測試資料一律虛構**：範例人名用「虛構角色甲」，地點用「虛構地點乙」，案號用「TEST-001」。不得將任何真實案件內容、人名、證件號碼、電話、住址、車號寫入程式、測試、文件或提交內容。
7. **每次提交為新案件**：不得使用全域狀態、快取或前案資料。每次提交產生新的 case_id。
8. **停止條件**：遇到下列任一情況，停止並回報，不得自行繞過（端點規則見第 0.10 點）：
   - 本地模型端點不可用，或非 loopback 位址。
   - LLM 輸出經 3 次重試仍不合格。
   - 手冊與藍圖衝突。
   - 需要判斷法律內容才能完成的步驟。
9. **參考程式**：`judicial2_flow_work_v0.2.tar.gz` 內有前期實作，可參考。其中 `pipeline/flow/questions_gen.py` 與 `pipeline/flow/report.py` **不得使用**（已作廢）。
10. **端點規則（C2 決定）**：
    - P0 至 P7 與所有單元測試使用 stub 端點。stub 位於 `tests/fixtures/stub_llm/`，由 `tests/fixtures/stub_llm/server.py` 啟動，只監聽 `127.0.0.1`。
    - stub 依請求標頭 `X-Stub-Fixture` 回傳同名 JSON 檔（`tests/fixtures/stub_llm/<name>.json`）。每個回應的最外層必須含 `"_stub": true`，且模型名稱固定為 `stub-fixed`。
    - stub 僅供測試。不得用於任何實際案件，不得把 stub 的回應當作真實法律判斷。
    - P8 必須改用真實 loopback 端點執行。若 P8 未執行，交付時必須標示「僅通過 stub 測試」。

## 3. P1：頁 1 輸入驗證

### 3.1 欄位（程式端）

| 欄位 | 必填 | 型別與規則 |
|---|---|---|
| 所別 | 是 | 字串，使用者輸入（受理報告抬頭）；無預設值，不得由系統推定（Q6：讓使用者自己填） |
| 文件類型 | 是 | 值域：`受理報告`、`告發報告`；由受理性質對應（見 3.3） |
| 受理性質 | 否 | 值域見手冊 4.2。頁 1 不必填（Q2：否）。若未填，Gate 1 路由判定為 UNKNOWN，流程停在 Gate 1「補充後進入」，要求承辦人補填 |
| 發生時間 | 是 | 字串，非空 |
| 發生地點 | 是 | 字串，非空 |
| 案情摘要 | 是 | 字串，非空 |
| 報告階段 | 否 | 值域：初報、續報、結報、更正、單一報告；預設「單一報告」 |
| 案號 | 否 | 頁 1 不收集。案號於 Gate 2 之後由使用者於完成階段輸入 |

未知欄位一律拒絕（T2）。不得靜默忽略。

### 3.2 摘要重複處理（Q1：a，原文）

案情摘要不做任何移除。受理報告「五、案情摘要」保留原文（v20 第 7.5 節第 2 點）。
- 摘要中出現與發生時間、發生地點相同的文字：不改動原文，僅於 warnings 記錄「摘要含重複之時間或地點」（提示用）。
- 摘要中的日期與發生時間不一致：保留原文，加 warning，不自行採用其一。

### 3.3 受理性質與文件類型對應（手冊 G2-R13）

| 受理性質 | 文件類型 |
|---|---|
| 受理、告訴、受理（依案號推定） | 受理報告 |
| 告發 | 告發報告 |
| 其他 | 不產出條陳 |

報案、通報、函送、移送、查獲、備案、申訴、保護令，依路由規則決定是否產出條陳（見 5.3）。

### 3.4 測試

- T1：必填欄位缺漏時拒絕。
- T2：未知欄位拒絕。
- T3：摘要中重複之發生時間與地點不被移除，僅記錄 warning 提示。
- T4：日期不一致時保留原文並加 warning。

## 4. P2：本地 LLM 介接層與機械檢查

### 4.1 介接規則
1. 端點從環境變數 `JUDICIAL2_LOCAL_LLM_ENDPOINT` 讀取。變數不存在時停止。P0 至 P7 測試時，此變數指向 stub（見第 0.10 點）。
2. 端點主機必須為 `127.0.0.1`、`localhost` 或 `::1`。否則拒絕（T5）。
3. 模型名稱從 `JUDICIAL2_LOCAL_LLM_MODEL` 讀取，未設定時停止。stub 模式下為 `stub-fixed`。
4. 呼叫格式採 OpenAI 相容 `/v1/chat/completions`。要求 JSON 輸出。
5. 每個 Gate 只呼叫一次 LLM（C-R01）。失敗時最多重試 2 次，共 3 次。

### 4.2 機械檢查（所有 Gate 共用）
1. JSON 可解析。
2. 必要欄位存在（依各 Gate 的 schema，見第 5 節）。
3. 值域正確（路由、候選狀態、告訴乃論等）。
4. warning 完整保留：下一 Gate 的輸入必須包含前一 Gate 全部 warning，只能新增，不得刪除或改寫。
5. unit_id 唯一，且後續 Gate 只引用 unit_id。
6. 問句句式（僅適用於所有產出之問句）：
   - 禁止是非問句：含「是否」「有沒有」「有無」「是不是」「對不對」「能不能」「可不可以」「會不會」「要不要」，或句尾為「嗎」。
   - 禁止引導式問句：含「難道」「對吧」「不是嗎」「沒錯吧」「你承認」「承認」「你應該」「你不可能」「你才是」。
7. 個資格式檢查（C-R17 機械檢查）：輸出中若出現符合台灣身分證字號格式或行動電話格式者，退回 LLM 重寫，不得自行遮罩後放行。
8. 不合格：退回 LLM 修正（同一 Gate 內，最多 2 次）。仍不合格則停止，回報哪一項不合格。

### 4.3 測試
- T5：非 loopback 端點被拒絕。
- T6：端點變數未設定時停止。
- T7：JSON 解析失敗時重試，第 3 次失敗後停止。

## 5. Gate 處理與輸出 schema

每個 Gate 的 LLM 呼叫包含：系統指令（規則摘要與引用條次）、本 Gate 輸入（JSON）、輸出 schema。LLM 必須在同一次回應中完成處理與檢查（C-R01），並在輸出中標示檢查結果。

### 5.1 Gate 1（P3）

**輸入**：頁 1 欄位、受理性質、所別、文件類型、通緝書（路由 B 之通緝查獲必附）。

**規則來源**：手冊第 6 節（G1-R01 至 G1-R24）、第 4 節（路由）、第 10 節（法條資料表）。

**輸出 schema**：
```json
{
  "gate": "G1",
  "case_id": "string",
  "version": "v1",
  "route": "A|B|C|D|E",
  "route_basis": {"受理性質": "", "有被害人": "是|否|UNKNOWN", "刑事行為": "是|否|不明", "案號": "string|UNKNOWN", "依據條次": ""},
  "units": {
    "victim": [{"unit_id": "", "時": "", "地": "", "物": "", "被害客體類型": "", "人": "", "報告人": "", "事": "", "是否有證人": "", "source_raw": ""}],
    "actor": [{"unit_id": "", "人": "", "行為人類型": "自然人|法人|機關", "事": "", "時": "", "地": "", "物": "", "法條標示": "", "source_raw": ""}]
  },
  "procedure_facts": {"告訴狀態": "", "追訴權狀態": "", "相關罪章檢核": "", "承辦人待辦": []},
  "warnings": [{"id": "G1-W01", "source_gate": "G1", "text": ""}]
}
```

**路由規則（P3 校驗，依手冊 13.1 與 4.3）**：

程式不判定路由，也不得依原始案情文字自行推定任何依據欄位。LLM 必須在 `route_basis` 中宣告依據欄位（有被害人、刑事行為、受理性質、案號）與路由。程式只核對「宣告的依據」與「宣告的路由」是否符合下列對照表。不一致時退回 LLM。

| 條件 | 應為路由 |
|---|---|
| 含刑事行為，有被害人，受理性質為受理、告訴、告發、受理（依案號推定） | A |
| 含刑事行為，無被害人，受理性質為受理、告訴、告發、查獲、受理（依案號推定） | B |
| 含刑事行為，受理性質為報案、通報、函送、移送，無案號，有被害人 | A（案號標 UNKNOWN） |
| 含刑事行為，受理性質為報案、通報、函送、移送，無案號，無被害人 | B（案號標 UNKNOWN） |
| 無刑事行為，有案號 | C |
| 行政裁處 | E |
| 其他 | D |

**停止條件（G1-R14）**：路由 B 之通緝查獲案件，若通緝書附件為「未附」，流程停在 Gate 1，回報使用者補附。

**測試**：
- T8：路由與上表不一致時退回。
- T9：通緝查獲未附通緝書時停止。
- T10：warning 在 Gate 1 完成後完整保留。
- T11：unit_id 重複時退回。
- T12：備案且含刑事內容時，承辦人待辦不為空。
- T13：輸出含個資格式時退回。

### 5.2 Gate 2（P4，僅路由 A）

**輸入**：Gate 1 之被害單元、程序事實、warnings。

**規則來源**：手冊第 7 節（G2-R01 至 G2-R15）。

**輸出 schema**：
```json
{
  "gate": "G2",
  "candidates": [{"unit_id": "", "案類": "", "法條": "", "法條狀態": "", "既遂未遂": "", "告訴乃論": "是|否|視關係而定|待查|NOT_APPLICABLE", "告訴乃論依據": "", "告訴狀態": "", "候選狀態": "MATCHED|NEED_REVIEW|UNKNOWN", "事實基礎": "", "理由": ""}],
  "victim_questions": [{"unit_id": "", "候選罪章": "", "核心問句": [], "判定缺少的補充問句": [], "事實釐清問句": [], "證據蒐集問句": [], "關係釐清問句": [], "時間序問句": [], "程序告知問句": [], "其他必要問句": []}],
  "procedure_questions": [{"unit_id": "", "管轄問句": [], "告訴期間問句": [], "告訴乃論問句": [], "程序要件問句": [], "其他法律要件問句": []}],
  "acceptance_draft": {"案由候選": [], "發生時間": "", "發生地點": "", "案情摘要": "", "證明單案號": "", "婦幼案號": ""},

```

**規則要點**：

- 無缺少者寫「無」或「目前無缺少」。
- 告訴乃論、追訴權、告訴期間只承接 Gate 1，不得重新判斷（G2-R15、G1-R15）。
- 案由欄列出候選，不得自行選定，不得沿用報告原案由（G2-R07 第 2 點）。

**測試**：
- T14：每個候選罪章至少一組被害人問句。
- T15：問句句式違規時退回（是非、引導）。
- T16：追訴權與告訴期間欄未被改寫（與 Gate 1 比對）。
- T17：多被害人各自產出（G2-R14）。
- T18：路由 A 以外不進入 Gate 2。

### 5.4 最終案情摘要（LLM，G2-FINAL）

**時點**：受理人員回答完被害人問句後，於 ANSWERING 結束時執行一次。

**輸入**：原案情摘要、Gate 1 事實單元、Gate 2 候選罪章與法條、受理人員之答案。

**輸出**：
```json
{"gate": "G2-FINAL", "final_summary": "string", "warnings": []}
```

**規則**：
- `final_summary` 用於受理報告「五、案情摘要」。
- 受理報告的案情摘要原則保留原文中之個資（v20 草案第二節，C-R17 之例外僅限受理報告）。
- 問句與待辦清單仍依 C-R17 精簡。
- 程式檢查：JSON 結構、`final_summary` 非空、不得出現非候選罪章之罪名詞。

## 6. P6：流程狀態機

### 6.1 狀態

```
INTAKE → GATE1 → [路由 A] GATE2 → ANSWERING → GATE2_FINAL_SUMMARY → COMPLETED → NUMBERED
                 [路由 B] DONE_ROUTE_B_PENDING_GATE3
                 [路由 C/D/E] DONE_RECORD
```

- `INTAKE`：頁 1 驗證通過。
- `GATE1`：Gate 1 完成並通過檢查。若為「補充後進入」，停在此狀態，補件後重跑 Gate 1。
- `GATE2`：路由 A 才進入。
- `ANSWERING`：使用者逐題回答被害人問句與程序問句，程式只檢查「全部已作答」與長度上限。
- `GATE2_FINAL_SUMMARY`：受理人員回答完畢後，Gate 2 依已確定之罪章候選，以 LLM 重新編寫最終案情摘要（見 5.4）。
- `COMPLETED`：產生完整受理條陳與筆錄內容。案號（Gate 2 之後取得）與被害人代號、婦幼案號為選填，於此階段一併輸入。
- `NUMBERED`：案號於 COMPLETED 階段未取得時，之後補填，產生最終受理條陳。
- `DONE_ROUTE_B_PENDING_GATE3`：路由 B 之 Gate 1 完成，Gate 3 待後續階段實作。
- `DONE_RECORD`：路由 C、D、E 之紀錄輸出完成（僅保留紀錄，不產出問句）。

### 6.2 規則
- 只能向前，不得跳過狀態。
- 不得回頭修改前 Gate 輸出（C-R11）。補充涉及前 Gate 事實時，開新版本（v2、v3），從 Gate 1 重跑（C-R13）。
- 同一案件之每次補件，同一 Gate 內重新檢查，不開新版本（C-R12 第 4 點）。

### 6.3 測試

## 7. P7：條陳渲染與案號步驟

### 7.1 模板
- 受理報告：`templates/wuxing/acceptance_v1.json`（括號已為全形，依 v19 7.5 固定文字，手冊正文括號待 v20）。
- 破獲條陳：`apprehension_no_victim.json`、`apprehension_with_victim.json`（待手冊納入，草案狀態，本階段僅保留檔案，不接入流程）。

### 7.2 渲染規則
1. 選填段落：整行只由選填欄位組成且全部為空，省略整行。
2. 案號段落：`post_gate2` 欄位為空時，括號內該項整項省略（例如只有證明單案號時，只顯示「證明單案號：…」）。括號內全部為空時，省略整段括號，保留「（一）依規定受理。」。
3. 必填欄位為空：拒絕渲染，不得推測補值。
4. 草稿模式：未填必填欄位以【待填】標示。
5. 固定文字不得改寫。

### 7.3 完成與案號
1. COMPLETED：渲染完整受理條陳。案號未取得者，依 7.2 第 2 點省略。
2. 筆錄內容：暫時格式「問 N ／答 N」，標示「待筆錄格式」。
3. NUMBERED：案號後補時由使用者填寫。系統不做格式檢核（Q11：使用者自行填寫，v20 C-R21 已修正）。
4. 案號段落顯示於條陳。

### 7.4 被害人代號、婦幼案號、165 案號（v20 第 7.6 節）
1. 被害人代號由公司系統提供，承辦人於完成階段輸入。系統不產生代號。頁 1 不收集代號（決定：不新增頁 1 欄位）。
2. 有代號即婦幼案件，婦幼案號欄位自動顯示並為必填（決定 A）。
3. 有代號但婦幼案號為空，拒絕完成，回報「已輸入被害人代號，婦幼案號為必填」。
4. 出現婦幼案號時，被害人姓名以代號呈現。
5. 婦幼相關法規清單見 v20 第 7.6 節第 4 點。Gate 2 案類候選落在該清單者，加 warning「婦幼案件，請確認代號與婦幼案號」。
6. 165 案號（Q7：a）：案由為詐欺時，系統提示承辦人確認，不自動顯示。
7. 媒體關注（Q8：a）：欄位預設「無」，承辦人可更改。

### 7.5 測試
- T27：案號段落省略時無空標籤。
- T28：必填欄位為空時拒絕。
- T29：固定文字與模板檔一致。
- T30：案號格式不符時加 warning，不阻擋。
