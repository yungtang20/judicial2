# JUDICIAL2 受理流程藍圖 v0.3（依手冊 v19 重寫，含 A、B、C2 決定）

修訂：依使用者說明，個資條款改為「Claude 不得記憶個資」，移除系統收集與遮罩的限制。

狀態：草案，供本地 AI 依手冊執行。本版本取代 v0.2。v0.1 已作廢。
依據：`rules/handbook/JUDICIAL2_GATES_MANUAL_2026-10-09-v19.md`。若本藍圖與手冊衝突，以手冊為準，並回報衝突。

---

## 0. 修改規則

1. 規則以手冊 v19 為準。不得自行新增、刪除或改寫規則條文。
2. 個資規則只適用於 Claude（執行者）的記憶：不得把個資寫入記憶檔、偏好檔、對話摘要或任何長期保存的位置。系統（表單、流程、條陳）依手冊處理案情所需之欄位，不因個資而限制收集。輸出依 C-R17 精簡個資。
3. 每一次提交都是新案件（C-R10）。不得沿用前案的事實、人物、warning、法條候選或問句。
4. 範例一律使用虛構值（如「虛構角色甲」「虛構地點乙」「TEST-001」）。不得把真實案件內容寫入藍圖、程式、測試或文件。
5. 固定文字（7.5 條陳格式）不得改寫。
6. 程式不做法律判斷。法律判斷由 LLM 依手冊執行，程式只做格式、結構、單元 ID、warning 與規則的機械檢查。
7. 本藍圖不列具體法條內容。法條只能引用法條資料表（第 10 節）的狀態與內容。

## 1. 架構原則

- **LLM 執行，程式檢查**：Gate 1、2、3 各由 LLM 處理。每個 Gate 的處理與檢查在同一次 LLM 呼叫完成（C-R01）。
- **程式只做機械檢查**：JSON 結構、必要欄位存在、unit_id 唯一、warning 不被刪除、版本號、路由值域、條陳模板是否可渲染。程式不判斷罪名、不判斷告訴期間。
- **路由（B 決定）**：程式不判定路由。LLM 須宣告依據欄位（有被害人、刑事行為、受理性質、案號）與路由，程式只核對兩者是否符合手冊 13.1 對照表。
- **LLM 只在本機執行**：所有案情內容只能送到本機（loopback）的模型端點。模型選型待定。
- **Gate 凍結**：Gate 輸出合格並進入下一 Gate 後不得回頭修改（C-R11）。

## 2. 流程總覽

```
[頁 1 輸入]
  發生時間、發生地點、案情摘要、受理性質、所別、文件類型
        │
        ▼
[前置檢查（程式）]  欄位齊全、個資格式偵測（見第 3 節）、所別與文件類型
        │
        ▼
[Gate 1（LLM）]  事實單元、路由 A/B/C/D/E、追訴權與告訴期間標示、路由 B 罪章檢核、承辦人待辦
        │  └─ 補充後進入 → 流程停在 Gate 1，使用者補件後同一 Gate 重新檢查
        ▼
   路由 A ─────────────┐
        │              │
        ▼              │
[Gate 2（LLM）] 案類候選、法條候選、告訴乃論、被害人筆錄問句、程序問句、條陳內容
        │              │
        ▼              │
[頁 2 填答] 使用者回答被害人問句與程序問句（作答者為被害人）
        │
        ▼
[頁 3 完成] 完整受理條陳 + 筆錄內容（輸出給公司電腦輸入）
        │
        ▼
[頁 3 案號] 使用者填回公司系統產生的案號 → 最終受理條陳

   路由 B ───→ [本階段止於 Gate 1，Gate 3 待後續階段]（A 決定）
   路由 C/D/E ─→ 依手冊處理，不產出涉嫌人或被害人問句
```

後續階段（尚未納入本次範圍）：涉嫌人問句（Gate 3）、破獲條陳、涉嫌人筆錄。

注意：手冊規定路由 B 不經 Gate 2，路由 A 才經過 Gate 2。被害人問句與涉嫌人問句分屬不同人，不得混用。

## 3. 頁 1 輸入與前置檢查

### 3.1 欄位

| 欄位 | 必填 | 說明 | 來源依據 |
|---|---|---|---|
| 所別 | 是 | 下拉選單，無預設值，不得由系統推定 | G2-R13、G1-R19 |
| 文件類型 | 是 | 依受理性質對應，見 3.3 | G2-R13 |
| 受理性質 | 是 | 值域見手冊 4.2（含保護令、申訴（性騷擾）） | 4.2、G1-R23、G1-R24 |
| 發生時間 | 是 | 自由文字，Gate 1 正規化（C-R15） | C-R15 |
| 發生地點 | 是 | 自由文字 | 6.2 |
| 案情摘要 | 是 | 自由文字 | 6.2 |
| 報告階段 | 否 | 初報／續報／結報／更正／單一報告，預設「單一報告」 | 6.5 報告階段 |
| 報案時間 | 否 | 由 Gate 1 自事實判定或標 UNKNOWN。手冊 6.5 有欄位，但不作為頁 1 必填 | 6.5 |
| 案號 | 否 | 頁 1 可空，標 UNKNOWN 並加 warning「案號未填，請承辦人補填」 | 4.3 第 4 點 |

**個資與本系統**：本系統可依手冊處理案情中出現的人、事、時、地、物。輸出（條陳、問句、待辦）依 C-R17 精簡。本藍圖不規定另外的個資收集限制。

### 3.2 前置檢查（程式）

1. 必填欄位齊全。
2. 不做個資遮罩或偵測。輸出精簡依手冊 C-R17，由 Gate 1 與 Gate 2 執行。
3. 所別與文件類型組合須有對應模板（G2-R13）。無對應模板者標 UNKNOWN，要求使用者指定。
4. 同一次提交只建立一個案件，案件 ID 每次新產生（C-R10、C-R13 之版本 v1）。

### 3.3 受理性質與文件類型對應（依 G2-R13）

| 受理性質 | 文件類型 |
|---|---|
| 受理、告訴、依案號推定之受理 | 受理報告 |
| 告發 | 告發報告 |
| 其他 | 不產出條陳 |

## 4. Gate 1（LLM）

### 4.1 輸出
依手冊 6.6 的結構輸出：路由結果、被害單元、行為單元、證人陳述、程序與其他要件事實（6.5）、承辦人待辦（如適用）、warnings。

### 4.2 程式檢查（機械）
1. JSON 結構符合 6.6，欄位不缺。
2. unit_id 唯一，且後續 Gate 只引用 unit_id。
3. 每個單元有 source_raw 與 warnings。
4. 路由值域為 A、B、C、D、E 之一。
5. 路由 B 且為通緝查獲時，檢查「通緝書附件」是否為「已附」。未附者，流程停在 Gate 1（G1-R14 第 3 點）。
6. 路由 C、D 備案含刑事內容時，承辦人待辦不得為空（G1-R22）。
7. 不符合 1～6 者，不得進入下一 Gate，回傳 LLM 修正或要求使用者補件。

### 4.3 「補充後進入」的實作
- 流程停在 Gate 1。
- 使用者補件後，由 Gate 1 重新呼叫 LLM 檢查，不開新版本（C-R12 第 4 點）。
- 若補件涉及前 Gate 事實，才開新版本（C-R11 第 4 點、C-R13）。

### 4.4 Warning 稽核
程式若因故遺漏 Gate 輸出的 warning，補回時須留稽核紀錄（C-R03 第 4 點）。稽核紀錄不列為 warning，不另編號。

---

## 5. Gate 2（LLM，僅路由 A）

### 5.1 輸出
依手冊 7.3：案類候選、法條候選（附法條資料表狀態）、告訴乃論、告訴期間判斷（承接 Gate 1）、追訴權狀態（承接 Gate 1）、被害人筆錄問句（依 G2-R05 之類別）、被害人程序問句（依 G2-R06）、條陳內容（依 G2-R07）、warnings。

### 5.2 問句要求（手冊 G2-R05）
- 每個候選罪章至少一組。
- 每組至少含：候選罪章、核心問句、判定缺少的補充問句。
- 其餘類別依案情增列：事實釐清、證據蒐集、關係釐清、時間序、程序告知、其他必要問句。
- 限被害人端客觀事實，不問行為人主觀，不作法律判斷。
- 無缺少者寫「無」或「目前無缺少」。

### 5.3 程式檢查（機械）
1. 每組問句含必要欄位。
2. 問句不得含證件號碼、電話（C-R17）。
3. 問句句式檢查：不得含是非問句（是否、有沒有、是不是、…嗎）與引導式問句（難道、對吧、你承認、你應該）。違反者退回 LLM 重寫。
4. 告訴乃論、追訴權、告訴期間只承接 Gate 1，不得重新判斷（G2-R15、G1-R15）。

### 5.4 條陳案由
依 G2-R07 第 2 點，案由欄列出案類候選，標示「候選」，不得自行選定，也不得沿用報告原案由（G1-R21 第 5 點）。

---

## 6. 頁 2：被害人填答

- 使用者逐題回答 Gate 2 產生的被害人問句與程序問句。
- 作答者為被害人，回答只限客觀事實。
- 程式只檢查「是否全部作答」與「回答長度上限」。不判斷回答內容是否正確。
- 回答內容屬案情補充。若補充涉及 Gate 1 事實，依 C-R12 第 4 點與 C-R11 第 4 點處理（開新版本，從 Gate 1 重跑）。

---

## 7. 頁 3：完成與案號

### 7.1 完成
- 產生完整受理條陳（依 7.5 固定格式，案號欄位保留為空，不顯示）。
- 產生筆錄內容（依被害人問句與回答）。格式待手冊補充，目前標示為「待筆錄格式」。
- 兩者交給公司電腦輸入，系統不直接送出。

### 7.2 案號
- 使用者把公司系統產生的案號填回。
- 系統只把案號填入條陳。案號格式依 C-R21 檢核，不符者保留原文並加 warning。
- 案號出現於條陳的位置依模板：證明單案號、婦幼案號。模板規則見第 8 節。

---

## 8. 條陳模板與渲染

### 8.1 模板檔（已存在，見 `templates/wuxing/`）
- `acceptance_v1.json`：受理報告，依手冊 7.5，括號已依決定改為全形。手冊 7.5 正文仍為半形，需以版本更新處理（見 9.2）。
- `apprehension_no_victim.json`、`apprehension_with_victim.json`：破獲條陳，手冊尚未納入，草案待確認（見 9.3）。

### 8.2 渲染規則（程式實作）
1. 選填段落：整行只由選填欄位組成且全部為空，省略整行。
2. 案號段落：案號欄位為空時，省略含該欄位的全形括號段落，只保留前段文字。
3. 必填欄位為空：拒絕渲染，不得推測補值。
4. 草稿模式：未填的必填欄位以【待填】標示。

### 8.3 婦幼案號與代號（已決定，見 9.1）
- 有婦幼案號時，被害人姓名以代號呈現。
- 代號由承辦人提供，系統不產生、不推定。

## 12. 測試要求

1. 頁 1：必填檢查、所別無預設、受理性質值域。
2. Gate 1 結構檢查：unit_id 唯一、路由值域、通緝書未附時停止。
3. Gate 2 問句檢查：是非問句與引導式問句被退回；無證件號碼與電話。
4. 條陳渲染：案號未產生時括號段落省略；必填為空時拒絕；固定文字不被改寫。
5. 新案件隔離：兩次提交之間不共享任何狀態。
6. 測試資料一律為虛構。
